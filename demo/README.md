# SnapPromo Live — จับสินค้าจากภาพไลฟ์

เดโมจับคู่สินค้าทีละเฟรมจากรูปภาพหรือวิดีโอ เริ่มที่ Catalog เพื่อเพิ่มสินค้า แล้วเปิด Detect เพื่อดูว่าสินค้าตัวไหนอยู่ตรงไหนในภาพ ใช้ Node.js 20.19 ขึ้นไป (แนะนำ Node.js 22 สำหรับโปรเจกต์นี้) รันคำสั่งในโฟลเดอร์ `demo/`

```powershell
npm install
if (!(Test-Path .env)) { Copy-Item .env.example .env }
# ใส่ OPENAI_API_KEY ใน .env ก่อนทดสอบกับ OpenAI
npm run dev
```

บน macOS/Linux ใช้ `cp -n .env.example .env` เปิด [Catalog](http://127.0.0.1:3030/catalog) หรือ [Detect](http://127.0.0.1:3030/detect) เปลี่ยนพอร์ตได้ด้วย `PORT` ในไฟล์ `.env` ซึ่ง Git จะข้ามให้ คีย์ใช้ฝั่งเซิร์ฟเวอร์เท่านั้น

### ทดลองตรวจจับ

1. เพิ่มรหัส ชื่อ ราคา คำอธิบายลักษณะที่มองเห็น และรูปอ้างอิง 1–3 รูปใน Catalog ระบบบันทึกที่ `data/catalog.json` และ `data/images/` รองรับ JPEG, PNG และ WebP ขนาดไม่เกินรูปละ 8 MB ระบบหมุนภาพตาม EXIF และแปลงเป็น JPEG ด้านยาวไม่เกิน 512 px ทั้งรูปอ้างอิงและเฟรม
2. เปิด Detect เพื่อใช้ตัวอย่างห้องครัวจริงที่นำภาพสินค้ามาวาง เลือกห้องครัวจำลอง หรืออัปโหลดภาพหรือวิดีโอของร้านเอง แล้วกดตรวจจับ หน้าเว็บใช้ **Choice + ภาพอย่างเดียว** ซึ่งจับคู่ถูก 54 จาก 57 กรณี (94.7%) ในชุดทดสอบสามร้าน [ผลรายวิธี](bench/results.md)
3. เมื่อ Decisions ตอบ หน้าเว็บแสดงชื่อสินค้า ความมั่นใจ คะแนนของสินค้าแต่ละตัว คะแนนของ `none` และโอกาสที่ผู้ขายกำลังยกสินค้า ถ้าเลือก `none` จะแสดง “ไม่พบสินค้าในระบบ”
4. ถ้าพบสินค้า ระบบหาตำแหน่งของ SKU นั้นต่อโดยอัตโนมัติ เมื่อได้พิกัด กรอบจะปรากฏบนเฟรมที่ส่งตรวจ หากหาตำแหน่งไม่ได้ ยังเห็นผลจับคู่และคะแนนเดิม

สำหรับ HTTP API และ eval วิธี Choice ส่งรหัส ชื่อ และคำอธิบายสินค้าทุกตัวเป็นตัวเลือกพร้อม `none` วิธี Reference ส่งคำถาม predicate ต่อสินค้า พร้อมรูปอ้างอิงใน `instructions` แล้วเลือกคะแนนสูงสุดตั้งแต่ 0.5 ขึ้นไป เมื่อเสมอกันจะเรียงตามลำดับในคลัง คะแนน Reference เป็นอิสระต่อกัน หากทุกคะแนนต่ำกว่าเกณฑ์ ระบบตอบ `none` และคืน `confidence: null` ทั้งสองวิธีถาม `held_up` ในคำขอเดียวกัน และให้ค่าเป็นจริงเมื่อ probability ≥ 0.5 การส่งข้อความประกอบจะเพิ่ม `input_text` ใน user message เดียวกับ `input_image`

### เรียกจากโค้ดหรือ HTTP

โมดูล [detectProduct](detect.ts) รับ `detectProduct(frameBuffer, method, text?, locate?)` โดย `frameBuffer` เป็นไบต์รูปที่ถอด base64 แล้ว เมื่อนำไปใช้กับ OBS ภายหลังจึงเรียกฟังก์ชันเดียวกับเว็บและ eval ได้

| Endpoint | ข้อมูล |
| --- | --- |
| GET /api/catalog | คืนอาร์เรย์สินค้า พร้อมชื่อไฟล์ JPEG ที่เปิดได้ทาง `/images/<filename>` |
| POST /api/catalog | JSON `{ id, name, price, description, images: [dataURL, ...] }` |
| DELETE /api/catalog/:id | ลบสินค้าและรูปอ้างอิง คืน HTTP 204 |
| POST /api/detect/frame | หน้า Detect ส่ง JSON `{ image: dataURL }` ครั้งเดียว ได้ `application/x-ndjson` บรรทัด `type: "match"` พร้อมผลจับคู่ ตามด้วย `type: "location"` พร้อม `bbox` และ `localization_status` แต่ละบรรทัดมี `latency_ms` นับจากต้นคำขอ |
| POST /api/detect | JSON `{ image: dataURL, method: "choice" หรือ "reference", text?: string, locate?: boolean }` |

ผลตรวจประกอบด้วย `product_id`, `product_name`, `confidence`, `top3: [{id,name,p}]`, `held_up` และ `latency_ms` ค่า `p` และค่าความมั่นใจแบบตัวเลขอยู่ในช่วง 0–1 หน้าเว็บแสดงเป็นเปอร์เซ็นต์ รหัส `none` สงวนไว้สำหรับผลไม่พบสินค้า

### เลือกเฟรมวิดีโอและดูกรอบ

เปิด [Detect](http://127.0.0.1:3030/detect) เลือกรูป หรือเปิดไฟล์ MP4/WebM ที่เบราว์เซอร์เล่นได้ เลื่อนไปยังเวลาที่ต้องการแล้วกด **จับเฟรมนี้และตรวจจับ** เบราว์เซอร์ส่งเฉพาะภาพ JPEG ณ เวลานั้น เมื่อ Decisions เลือกสินค้าได้ เซิร์ฟเวอร์ส่งชื่อและคะแนนกลับทันทีก่อนเรียก Responses API ด้วยเฟรมและรูปอ้างอิงของ SKU เพื่อประมาณกรอบ ระบบล้างกรอบเดิมเมื่อเปลี่ยนไฟล์หรือเล่นวิดีโอต่อ

สำหรับ `POST /api/detect` ให้ส่ง `locate: true` เมื่อต้องการกรอบ สำหรับ `POST /api/detect/frame` ระบบหากรอบอัตโนมัติ เมื่อได้ `localization_status: "found"` ให้วาด `bbox: {x,y,width,height}` โดยแต่ละค่าเป็นสัดส่วน 0–1 ของภาพที่ปรับทิศทางแล้ว วัดจากมุมซ้ายบน เช่น `x: 0.25` หมายถึงขอบซ้ายของสินค้าอยู่ที่หนึ่งในสี่ของความกว้างภาพ สถานะ `skipped` คือข้ามขั้นตอนนี้, `not_found` คือโมเดลระบุตำแหน่งไม่ได้ และ `unavailable` คือบริการหากรอบขัดข้อง ทั้งสามสถานะคืน `bbox: null` การเลื่อนไปเวลาใหม่ต้องกดตรวจเฟรมนั้นอีกครั้ง

สำหรับคลังเดโม 26 รายการ ลอง [คลิปทดสอบ 4 วินาที](bench/location/two-products-sample.mp4) เปิดที่ 1 วินาทีเพื่อดูเครื่องปั่นด้านซ้าย และ 3 วินาทีเพื่อดูเตาไฟฟ้าด้านขวา คลิปประกอบจากภาพสาธิตคนละมุมกับรูปอ้างอิง ระบบเลือก SKU หลักหนึ่งตัวต่อเฟรมและประมาณกรอบของสินค้าตัวนั้น การหากรอบใช้คำขอ Responses เพิ่มเมื่อพบ SKU และเฟรมมีรายละเอียดภาพ

หน้า Detect ใช้ GPT-6 Luna สำหรับเลือก SKU และใช้ GPT-6.2 Sol สำหรับหากรอบโดยดูรูปอ้างอิงกับเฟรมที่มีเส้นพิกัด เลือก Sol จากความเร็วเฉลี่ย 3.04 วินาทีและกรอบที่ผ่านเกณฑ์ IoU ≥ 0.50 จำนวน 10/12 กรณีที่มีสินค้า เทียบกับ GPT-6.2 Astra ที่ผ่าน 11/12 ในเวลาเฉลี่ย 7.01 วินาที (สูงสุด 58.11 วินาที) และ Luna ที่ผ่าน 7/12 ในเวลาเฉลี่ย 6.47 วินาที ทั้งสามรุ่นเว้นกรอบถูกใน 6/6 กรณีที่สินค้าเป้าหมายไม่อยู่ในเฟรม ตัวเลขนี้วัดเมื่อระบุ SKU ให้แล้ว [ผลรายรุ่นและรายเฟรม](bench/location/model-comparison.md) · [คู่มือรุ่นล่าสุดของ OpenAI](https://developers.openai.com/api/docs/guides/latest-model)

การทดสอบเส้นทางวิดีโอก่อนเปลี่ยนรุ่นตีกรอบจาก Astra เป็น Sol ทำผ่าน Chrome ที่ความกว้าง 390 px ชื่อเครื่องปั่นปรากฏใน 2.44 วินาที และกรอบด้านซ้ายปรากฏที่ 5.72 วินาทีหลังคลิก ส่วนชื่อเตาไฟฟ้าปรากฏใน 0.38 วินาที และกรอบด้านขวาปรากฏที่ 3.69 วินาทีหลังคลิก ทั้งสองครั้งใช้ API จริง [ภาพกรอบเตาไฟฟ้า](bench/location/stream-video-example.png) · [เวลาที่วัดจากหน้าเว็บและเซิร์ฟเวอร์](bench/location/stream-video-smoke.json)

### ทดลองกับพื้นหลังห้องครัว

หน้า Detect เปิดด้วยภาพถ่ายห้องครัวที่นำรูปเตาไฟฟ้ามุมที่สี่มาวางบนเคาน์เตอร์ด้านซ้าย ตัวอย่างที่สองใช้ ImageGen สร้างฉากห้องจากรูปอ้างอิงเครื่องปั่น ระบบเริ่มเรียก API เมื่อกดตรวจจับ และส่งเฉพาะไบต์ภาพในขั้นจับคู่ [ภาพถ่ายห้องของ amslerPIX](https://commons.wikimedia.org/wiki/File:Kitchen_Cabinets_-_Sink.jpg) · [สัญญาอนุญาต CC BY 2.0](https://creativecommons.org/licenses/by/2.0/) · [แหล่งสินค้า รายละเอียดการประกอบภาพ และตำแหน่งเฉลย](bench/location/room-photo-source.json)

วัดผ่าน API จริงกับคลังเดโม 26 รายการ ตัวเลขเป็นการรันหนึ่งครั้งต่อภาพ ค่า IoU วัดส่วนทับซ้อนของกรอบทำนายกับกรอบเฉลย ตั้งแต่ 0 ถึง 1 เวลาตีกรอบเริ่มนับหลังรู้ SKU แล้ว

| ภาพ | ผลจาก Choice | ความมั่นใจ | เวลาจับคู่ | เวลาตีกรอบด้วย Sol | IoU ของ Sol |
|---|---|---:|---:|---:|---:|
| ภาพถ่ายห้องครัว + เตาไฟฟ้า | เตาไฟฟ้าหน้าเรียบ | 81% | 533 ms | 2,436 ms | 0.991 |
| ห้องครัวจำลอง + เครื่องปั่น | เครื่องปั่นแบบตั้งโต๊ะ | 99% | 603 ms | 2,870 ms | 0.979 |
| ภาพถ่ายห้องเดิมก่อนวางเตา | ไม่พบสินค้าในระบบ | 92% | 405 ms | ข้ามในหน้าเว็บ | — |

ในการกดตรวจจับเตาบน Chrome อีกครั้ง หน้าจอแสดงชื่อที่ 1.14 วินาทีหลังคลิกและกรอบที่ 3.62 วินาที ภาพห้องว่างใช้ตรวจเพิ่มเติมว่าหากระบุชื่อเตาให้โมเดลทั้งคู่บนภาพนั้น Sol และ Astra ก็เว้นกรอบ [ภาพผลจากหน้าเว็บ](bench/location/room-example.png) · [เวลาจริงจาก Chrome](bench/location/room-smoke.json) · [ผลเต็มของทั้งสองโมเดล](bench/location/room-results.json)

จาก `demo/` รัน `node --import tsx bench/location/room-check.ts` เพื่อวัดทั้งสามภาพอีกครั้งกับ API โดยใช้คลังเดโมที่มี SKU ตาม [เฉลย](bench/location/room-annotations.json)

### เพิ่มสินค้าตัวอย่าง

สินค้ารหัส `kit-*` เป็นเครื่องครัวสาธิต 23 รายการ ราคาตั้งขึ้นเพื่อใช้ในเดโม ชื่อและคำอธิบายภาษาไทยอ้างอิงลักษณะที่มองเห็นในภาพ ชุดทดสอบมีภาพเครื่องปั่นตั้งโต๊ะและเตาไฟฟ้ามุมที่สี่ซึ่งแยกไว้จากสามภาพอ้างอิง ข้อความข้างภาพเป็นคำพูดสมมติสำหรับลอง eval [แหล่งภาพเครื่องครัว DummyJSON](https://dummyjson.com/products/category/kitchen-accessories)

วางภาพจริง 1–3 รูปต่อโฟลเดอร์ใน `data/seed/chili/` (น้ำพริกเผา), `data/seed/soap/` (สบู่สมุนไพร) และ `data/seed/basket/` (ตะกร้าสาน) แล้วรัน `npm run seed` ปรับชื่อ ราคา และลักษณะบรรจุภัณฑ์ใน [seed script](seed.ts) ให้ตรงของจริงก่อนรัน สคริปต์ข้ามโฟลเดอร์ว่างและรหัสที่มีอยู่แล้ว

### ทดสอบและวัดผล

```text
eval/frames/
  chili/01.jpg
  chili/01.txt
  none/02.jpg
  none/02.txt
```

ชื่อโฟลเดอร์คือรหัสคำตอบที่ถูกต้อง หรือ `none` สำหรับเฟรมที่ไม่มีสินค้าในคลัง ข้อความในไฟล์ UTF-8 `.txt` ชื่อเดียวกับรูปคือบริบทที่แม่ค้าพูดหรือผู้ใช้เห็นในเวลานั้น ใช้เฟรมคนละภาพกับรูปอ้างอิง และหลีกเลี่ยงการคัดลอกรหัสเฉลยมาเป็นข้อความ

```sh
npm test
npm run typecheck
npm run eval
```

`npm test` ใช้ API จำลองในเครื่อง ส่วน `npm run eval` เรียก Decisions จริงเมื่อมีชุดภาพและคีย์ พร้อมพิมพ์ตารางและเขียน [eval/results.md](eval/results.md) สำหรับเฟรมที่มีข้อความจะมี 4 คำขอต่อเฟรม (2 วิธี × 2 รูปแบบ) เฟรมที่ขาดข้อความใช้ 2 คำขอ ถ้าข้อความมีเพียงบางเฟรม รายงานเพิ่มแถวภาพอย่างเดียวเฉพาะชุดที่มีข้อความเพื่อเปรียบเทียบบนเฟรมเดียวกัน แถวนี้นำผลเดิมมาคำนวณซ้ำ

Accuracy คือจำนวนทายรหัสถูกหารด้วยจำนวนคำขอตรวจจับในแถวนั้น โดยนับข้อผิดพลาดในตัวหารและรายงานแยกใน Errors เวลาเฉลี่ยและสูงสุดวัดตั้งแต่เริ่มตรวจจับจนได้ผลหรือข้อผิดพลาด รวมการเตรียมภาพและเรียกโมเดล ตัวอย่างผลจากการรันกับโฟลเดอร์ว่างก่อนใส่ชุดทดสอบจริง

| วิธี | ข้อมูลที่ส่ง | Accuracy | เฉลี่ย (ms) | สูงสุด (ms) | Requests | Errors |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| choice | ภาพอย่างเดียว | — | — | — | 0 | 0 |
| choice | ภาพ + ข้อความ | — | — | — | 0 | 0 |
| reference | ภาพอย่างเดียว | — | — | — | 0 | 0 |
| reference | ภาพ + ข้อความ | — | — | — | 0 | 0 |
