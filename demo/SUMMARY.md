# SnapPromo Live — สรุปเดโมจับสินค้าจากภาพไลฟ์

สถานะ ณ วันที่ 21 พฤศจิกายน 2026 · [เปิดหน้า Detect](http://127.0.0.1:3030/detect) · [เปิด Catalog](http://127.0.0.1:3030/catalog)

เดโมตอบสองคำถามตามลำดับ **“ในเฟรมนี้มีสินค้าตัวไหนของร้าน”** และ **“สินค้านั้นอยู่ตรงไหน”** หน้า Detect ใช้ GPT-6 Luna จับคู่แบบ Choice จากภาพอย่างเดียว ทำถูก **54/57 กรณี (94.7%)** ในสามร้านจำลอง จากนั้น GPT-6.2 Sol หากรอบของสินค้าที่เลือกได้ ผ่านเกณฑ์ **10/12 กรณีที่มีสินค้า** และใช้เวลาเฉลี่ย **3.04 วินาที** ในชุดวัดกรอบ ผู้ชมเห็นชื่อและคะแนนได้ตั้งแต่ขั้นแรก ส่วนกรอบค่อยปรากฏบนเฟรมเดิม [ผลจับคู่สินค้า](bench/results.md) · [ผลตีกรอบ](bench/location/model-comparison.md)

## สิ่งที่ทีมเปิดลองได้

| หน้า | วิธีใช้ | สิ่งที่ได้ |
|---|---|---|
| Catalog | เพิ่มรหัส ชื่อ ราคา ลักษณะที่มองเห็น และรูปอ้างอิง 1–3 รูปต่อสินค้า | คลังสินค้าของร้าน พร้อมดูและลบรายการ |
| Detect | กดตรวจภาพห้องครัวตัวอย่าง อัปโหลดรูป หรือหยุดไฟล์ MP4/WebM ที่เฟรมต้องการ | ชื่อสินค้าหลักหนึ่งตัวหรือ “ไม่พบสินค้าในระบบ” ความมั่นใจ อันดับและคะแนนรายสินค้า ค่า `held_up` และเวลาประมวลผล |
| กรอบบนภาพ | เมื่อพบสินค้า ระบบส่งเฟรมกับรูปอ้างอิงของ SKU นั้นให้ Sol | กรอบปรากฏอัตโนมัติ หากหากรอบไม่ได้ยังอ่านผลจับคู่ได้ เมื่อเปลี่ยนเฟรมระบบล้างผลเดิม |

การเปิดหน้าตัวอย่างยังไม่เรียกโมเดล ผู้ใช้กดตรวจหนึ่งครั้งต่อเฟรม ขอบเขตปัจจุบันคือภาพนิ่งและเฟรมที่เลือกจากไฟล์วิดีโอ ส่วนการรับภาพต่อเนื่องจาก OBS และการติดตามสินค้าข้ามเฟรมเป็นงานต่อยอด [คู่มือใช้งานและ API](README.md)

## ผลจับคู่สินค้าและผลที่มีความหมายต่อการขาย

ชุดหลักมี 57 กรณีจาก 28 กลุ่มภาพต้นทางในร้านเครื่องครัว เสื้อผ้า และอิเล็กทรอนิกส์ ทดลอง 4 วิธี รวม 228 คำขอ แต่ละเฟรมเทียบเฉพาะคลังของร้านนั้น ตารางนับคำขอที่ผิดพลาดในตัวหาร

| วิธี | เลือก SKU หรือ `none` ถูก | เวลาจับคู่เฉลี่ย | ข้อผิดพลาดจาก API |
|---|---:|---:|---:|
| **Choice + ภาพอย่างเดียว** | **54/57 (94.7%)** | **435 ms** | 0 |
| Choice + ภาพและข้อความ | 53/57 (93.0%) | 417 ms | 0 |
| Reference + ภาพอย่างเดียว | 43/57 (75.4%) | 943 ms | 3 |
| Reference + ภาพและข้อความ | 47/57 (82.5%) | 802 ms | 0 |

Choice ภาพล้วนตอบถูกในร้านเครื่องครัว **14/14** เสื้อผ้า **22/23** และอิเล็กทรอนิกส์ **18/20** จาก 39 เฟรมที่มีสินค้า จับคู่ถูก 37 และตอบว่าไม่พบ 2 เฟรม ได้แก่ พาวเวอร์แบงก์ในภาพมืดเบลอและเสื้อทีมที่พับระหว่างส่งมือ จาก 18 เฟรมที่ไม่มีสินค้าในคลัง ระบบขึ้นสินค้าผิด 1 ครั้ง เมื่อเห็น iPhone 4 แล้วเลือก iPhone X โดยเฉพาะกลุ่มภาพถ่ายสถานการณ์จริงขนาดเล็ก วิธีนี้ถูก **3/5** หลายกรณีในชุดหลักดัดแปลงจากภาพต้นทางเดียวกัน จึงยังต้องวัดซ้ำกับไลฟ์จริงหลายรอบขาย [ผลแยกร้านและสภาพภาพ](bench/results.md) · [วิเคราะห์กรณีที่พลาด](bench/findings.md)

## ทำไมเดโมเลือก Sol สำหรับตีกรอบ

ให้แต่ละรุ่นดูเฟรม รูปอ้างอิง และ SKU เป้าหมายเดียวกัน วัด 18 คู่สินค้า–เฟรม กรอบถือว่าผ่านเมื่อพื้นที่ซ้อนทับหารด้วยพื้นที่รวมของกรอบทำนายและกรอบเฉลย หรือ IoU มีค่าตั้งแต่ 0.50 ขึ้นไป การวัดนี้เริ่มหลังทราบ SKU แล้ว เวลาเฉลี่ยข้ามภาพสีล้วนที่ตรวจได้ในเครื่อง

| รุ่นตีกรอบ | กรอบผ่านใน 12 กรณีที่มีเป้าหมาย | กรอบผิดใน 6 กรณีที่ไม่มีเป้าหมาย | เวลาเฉลี่ย | เวลาสูงสุด |
|---|---:|---:|---:|---:|
| **GPT-6.2 Sol** | **10/12** | **0/6** | **3.04 วินาที** | 8.64 วินาที |
| GPT-6.2 Astra | 11/12 | 0/6 | 7.01 วินาที | 58.11 วินาที |
| GPT-5.4 | 8/12 | 0/6 | 4.39 วินาที | 7.43 วินาที |
| GPT-6 Luna | 7/12 | 0/6 | 6.47 วินาที | 15.15 วินาที |

Sol เร็วที่สุดโดยเฉลี่ย ส่วน Astra ได้กรอบผ่านเพิ่มอีกหนึ่งกรณี คือเสื้อทีมที่กำลังส่งมือ ทั้งสี่รุ่นพลาดพาวเวอร์แบงก์ในภาพมืดเบลอ [เปรียบเทียบกรอบรายภาพ](bench/location/model-comparison.md)

รายงานก่อนเลือกสี่รุ่นนี้เริ่มจาก GPT-4.1-mini ที่ผ่าน 2/8 และให้กรอบผิด 3/4 เมื่อไม่มีเป้าหมาย การทดลอง GPT-5.4 สองรอบบนชุดแรกผ่าน 5/8 และให้กรอบผิด 0/4 ทั้งสองรอบ ส่วนชุดภาพใหม่ผ่าน 3/4 และเว้นกรอบถูก 2/2 ตัวเลขเหล่านี้มาจากการเรียก API คนละรอบกับตารางข้างบน [ผลเริ่มต้น](bench/location/results.md) · [ทดลองปรับวิธีตีกรอบ](bench/location/candidate-results.md) · [ผล GPT-5.4 รอบถัดมา](bench/location/production-results.md) · [ชุดภาพใหม่](bench/location/validation-results.md)

## ผลบนภาพห้องครัวที่เปิดลองในหน้าเว็บ

ใช้คลังเดโม 26 รายการ ขั้นจับคู่เห็นเพียงภาพ แต่ละแถวเป็นการเรียก API หนึ่งรอบต่อวิธี ภาพถ่ายห้องครัวใช้ห้องเดียวกันก่อนและหลังนำภาพเตามาวาง จึงตรวจได้ว่าระบบตอบอย่างไรเมื่อเอาสินค้าออก

| เฟรม | ผลที่ระบบเลือก | ความมั่นใจในคำตอบ | เวลาจับคู่ | เวลาตีกรอบเพิ่มด้วย Sol | IoU |
|---|---|---:|---:|---:|---:|
| ภาพถ่ายครัวจริง + เตาบนเคาน์เตอร์ซ้าย | เตาไฟฟ้าหน้าเรียบ | 81% | 533 ms | 2,436 ms | 0.991 |
| ครัวที่สร้างด้วย ImageGen + เครื่องปั่น | เครื่องปั่นแบบตั้งโต๊ะ | 99% | 603 ms | 2,870 ms | 0.979 |
| ภาพถ่ายครัวเดิมก่อนวางเตา | ไม่พบสินค้าในระบบ | 92% | 405 ms | หน้าเว็บข้าม | — |

เมื่อกดตรวจเตาผ่าน Chrome อีกครั้ง ชื่อปรากฏบนหน้าจอ **1.14 วินาที** หลังคลิก และกรอบปรากฏที่ **3.62 วินาที** หลังคลิก ผลกรอบครั้งนั้นมี IoU 0.9765 ภาพครัวจริงถ่ายโดย amslerPIX ภายใต้ CC BY 2.0 และนำมาประกอบกับภาพสินค้า [ภาพพร้อมกรอบ](bench/location/room-example.png) · [ผลวัดจากเบราว์เซอร์](bench/location/room-smoke.json) · [ผลวัดสามฉาก](bench/location/room-results.json) · [เครดิตภาพและวิธีประกอบ](bench/location/room-photo-source.json)

## สิ่งที่พบจากการทดลองเสริม

- **ข้อมูลที่ร้านลงไว้** ในชุดย่อย 25 ภาพ Choice ใช้ชื่ออย่างเดียวถูก 23/25 และชื่อพร้อมคำอธิบายก็ถูก 23/25 ชื่อสินค้าในชุดนี้มักระบุสี ลาย หรือรุ่นอยู่แล้ว ส่วน Reference ใช้รูปแรกถูก 20/25 และใช้รูปทั้งหมดถูก 19/25 [ผลเปรียบเทียบข้อมูลสินค้า](bench/listing-inputs.md)
- **AI ช่วยลงสินค้า** ทดลองให้ AI ร่างคำบรรยายไทยจากชื่อและรูปของสาม SKU พบว่า 2/3 ร่างต้องแก้คำหรือเอารายละเอียดที่ยืนยันจากภาพยากออก ก่อนให้ร้านอนุมัติ [ตัวอย่างร่างและผลตรวจ](bench/drafts/review.md)
- **ผู้ขายกำลังยกสินค้า** การถามถึงท่าทางที่เห็น เช่น ชูโทรศัพท์หรือกางเสื้อ ช่วยให้ `held_up` ตอบถูกจาก 3/5 เป็น 5/5 บนภาพอิสระห้าภาพ ใช้เกณฑ์ความน่าจะเป็น 0.5 [ผลทดลองรายท่าทาง](bench/actions/results.md)
- **กติกาขึ้นป้ายขาย** เมื่อจำลองย้อนหลังด้วยภาพล้วน การขึ้นป้ายทันทีตาม Choice ถูก 37/38 ครั้ง ถ้ารอ Choice และ Reference เลือกตรงกัน ป้ายที่ขึ้นถูก 29/29 ครั้ง แต่มีสินค้าอีก 10/39 เฟรมที่ต้องพักป้าย กติกาสองโมเดลนี้เป็นการทดลองสำหรับงานไลฟ์ในอนาคต [ผลจำลองการขึ้นป้าย](bench/policy.md)

## รัน ทดสอบ และต่อกับระบบร้าน

รันจากโฟลเดอร์ `demo/` ด้วย Node.js ตั้งแต่ 20.19 ขึ้นไป

```powershell
npm install
if (!(Test-Path .env)) { Copy-Item .env.example .env }
# ตั้ง OPENAI_API_KEY ใน .env แล้วเริ่มเซิร์ฟเวอร์
npm run dev
```

| คำสั่ง | ใช้ทำอะไร |
|---|---|
| `npm test` และ `npm run typecheck` | ผลการตรวจเดโมครั้งล่าสุดผ่าน 12/12 เทสต์และผ่าน TypeScript ครอบคลุมเกณฑ์คะแนน ผลเสมอ `none` การส่งผลก่อนกรอบ และการยกเลิกเมื่อเปลี่ยนเฟรม |
| `npm run seed` | เพิ่มสินค้าตัวอย่างสามรหัสจากรูปที่ทีมวางใน `data/seed/` |
| `npm run eval` | วัดกับคลังปัจจุบันและไฟล์ `eval/frames/<product_id>/*.jpg` ใช้โฟลเดอร์ `none` สำหรับภาพลบและไฟล์ `.txt` ชื่อเดียวกับรูปสำหรับข้อความประกอบ รายงานที่บันทึกไว้เป็นรอบที่มี 0 เฟรม ตัวเลข 57 กรณีมาจากชุดร้านจำลอง [รายงาน eval](eval/results.md) |
| `npm run bench -- --report-only` | สร้างรายงานสามร้านซ้ำจากผลที่เก็บไว้ โดยไม่เสียค่า API |
| `node --import tsx bench/location/room-check.ts` | วัดสามฉากห้องครัวซ้ำผ่าน API จริง |

**Built during hackathon** ทีมสร้างหน้า Catalog และ Detect โมดูล `detectProduct(frameBuffer, method)` การตอบแบบสตรีม ระบบตีกรอบ และชุดประเมิน คลังสินค้าดู เพิ่ม และลบผ่าน `/api/catalog` หน้า Detect ใช้ `POST /api/detect/frame` เพื่อรับ `match` ก่อน `location` ส่วน `POST /api/detect` รองรับทั้ง Choice และ Reference พร้อมข้อความประกอบและตัวเลือกหากรอบ [รายละเอียด API และตัวอย่างการรัน](README.md)

**Existing tools used** เดโมใช้ Node.js, TypeScript, Express, HTML/CSS/JavaScript, OpenAI Node SDK และ sharp เพื่อหมุนภาพตาม EXIF และแปลงเป็น JPEG ด้านยาวไม่เกิน 512 px คลังอยู่ใน `data/catalog.json` รูปอยู่ใน `data/images/` และเซิร์ฟเวอร์อ่านคีย์จาก `.env` ที่ Git ข้าม [คู่มือเทคนิค](README.md)
